Unity AI Gateway · self-service provisioning

How the request flows, and where the tags live

A user requests an endpoint, membership is verified against their Entra group, they use it, tags land in three queryable places, and a daily job retires it after 30 days. Tables, columns, and calls are verified against e2-demo-field-eng; the governance gate and cleanup job are the recommended target design.

Governance & Unity Catalog privileges enforced at this step
  1. Entra → SCIM group check. The team a user picks maps to an Entra ID group synced into Databricks via SCIM. Provisioning is allowed only if the caller is a member — e.g. selecting data-science-rnd requires membership in the data-science-rnd Entra group. Verify with the SCIM Groups / current-user membership API before the create call.
  2. Endpoint ACLs on create. Grant the team's group CAN_QUERY and the requester CAN_MANAGE (PATCH /api/2.0/permissions/serving-endpoints/{id}) so the endpoint is visible and usable to the right people — not just the app's service principal.
  3. UC-aligned attribution. The cost_center / team / project tags mirror the group's cost center from the governed UC table, so spend and access share one identity.
  4. Lifecycle tag. A delete_after (created + 30 days) tag is stamped for the cleanup job in Phase 4.

3 · STORE & RETRIEVE

Where the tags live — and how to read them

A · Source of truth
The endpoint object
Set at creation; real-time; authoritative.
The tags[] array on the serving endpoint. Retrieve via REST / CLI / SDK, or the endpoint page in the UI.
# CLI / REST — returns tags immediately
databricks api get \
 /api/2.0/serving-endpoints/$NAME
# → tags: [{cost_center: CC-8820},
#          {delete_after: 2026-09-17}, …]
B · Cost attribution
system.billing.usage
Tags copied into custom_tags; keyed by usage_metadata.endpoint_name.
Endpoint tags propagate into the custom_tags map for chargeback. ⏱ billing data lags ~hours
SELECT custom_tags['cost_center'],
       custom_tags['team'],
       SUM(usage_quantity) AS dbus
FROM system.billing.usage
WHERE billing_origin_product=
      'MODEL_SERVING'
  AND usage_unit='DBU'
GROUP BY 1,2 ORDER BY dbus DESC
C · Usage tracking
system.serving.*
Per-request usage. Tags are joined in, not stored here.
endpoint_usage (requester, tokens, status, usage_context) joins served_entities on served_entity_id → endpoint_name.
SELECT e.endpoint_name, u.requester,
       u.status_code, u.output_token_count
FROM system.serving.endpoint_usage u
JOIN system.serving.served_entities e
  USING (served_entity_id)
WHERE e.endpoint_name = $NAME
4 · LIFECYCLE

Automatic 30-day cleanup

Databricks Job · daily cron
Cleanup job
Scheduled once/day (e.g. 02:00). Runs the sweep below.
→
Scan
List endpoints + tags
Read delete_after off every serving endpoint.
→
Evaluate
Past expiry?
today > delete_after → the 31st day onward.
→
Act
Delete endpoint
DELETE /serving-endpoints/{name}. Skip if still within 30 days.
Cleanup logic (target design — a scheduled Databricks Job)
# runs daily; deletes endpoints whose 30-day TTL has passed
for ep in list_serving_endpoints():
    d = ep.tags.get("delete_after")          # e.g. 2026-09-17
    if d and date.today() > date.fromisoformat(d):
        delete_serving_endpoint(ep.name)          # day 31 → removed
Gate — Entra/SCIM membership decides who may provision for a team. Store A/B/C — live truth · cost rollup · request usage. Lifecycle — delete_after tag + daily job = automatic 30-day retirement.
